## 0. 结论

**一句话**：内核（`core:git`）的工程质量明显高于一般个人项目——二进制格式用真实 git 对拍、并发有锁、迁移不 destructive、insets 处理有取舍说明；但**存在两条静默丢数据的路径**，且文档与 CI 有"说了没做"的夸大。先修数据安全，再谈体验。

| 维度 | 评分 | 判断依据 |
|---|---|---|
| `core:git` 内核 | **8.5 / 10** | 对象/index/pack 都有格式校验与 SHA-1 复核；diff/merge 有退化保护；缺 gc、缺流式大对象 |
| 数据层与安全 | **7.5 / 10** | AES-256-GCM + KeyStore、原子 rename、Room 不 destructive；DAO 有 3 张表从未写入 |
| UI / ViewModel | **6.5 / 10** | 状态建模克制、组件库统一；并发刷新互相覆盖、错误态有死代码 |
| 文档 | **5.5 / 10** | README 结构清晰；CI 描述与设计文档大面积过期 |
| 测试 | **6.0 / 10** | 89 个单测、含真实 git 对拍；**0 个 androidTest**，传输层错误路径与 UI 层几乎空白 |
| 工程化 | **7.0 / 10** | 一键构建脚本、签名、mapping、tag 驱动版本；CI 不跑 test/lint |

## 1. P0：会丢数据 / 可绕过安全

### 1.1 `pull` 快进时静默覆盖未提交改动（已用测试复现）

**证据**：`core/git/.../GitRepo.kt:341-344` 先判断能否快进并直接 `checkoutTreeClean(targetCommit.tree)`，**第 350 行才检查工作区是否干净**。`checkoutTreeClean → checkoutTree`（`:670`）无条件把 tree 里每个文件写回工作区。

**复现**（我写的探查测试，已跑通）：

```
base: a.txt = "v1"  →  远端分支 ahead: a.txt = "v2-remote"
本地 main 把 a.txt 改成 "LOCAL-DIRTY"（未提交）
repo.merge(ahead, ...)  →
  PROBE status=FAST_FORWARD
  PROBE worktree=v2-remote     ← 本地改动没了，且没有任何异常
```

**影响**：用户改了文件没提交，点「同步 → 拉取」，UI 提示"已更新到 master（新增 N 个对象）"（`RepoDetailViewModel.kt:242`），改动无声消失。这是本项目目前最严重的问题。

**建议**：
1. 把 `val dirty = status()...` 提到 `headOid == null` 之后、所有分支判断之前（`checkoutBranch` 已经是这个顺序，`GitRepo.kt:106`，两处不一致）；
2. 补一条回归测试：脏工作区 + 可快进 → 必须抛 `DirtyWorkTree`；
3. 若要照顾"改动不冲突就想拉"的场景，可后续再做 git 式的 stash-then-merge，但**不能默认覆盖**。

### 1.2 编辑器「保存并退出」大概率根本没保存

**证据**：`feature/editor/.../EditorScreen.kt:160-164`

```kotlin
onConfirm = {
    exitDialog = false
    viewModel.save()   // 只是 launch 一个协程
    onBack()           // 立刻 pop，NavBackStackEntry 销毁 → viewModelScope 取消
}
```

`save()`（`EditorViewModel.kt:168`）里 `viewModelScope.launch { ... repository.saveFile(...) }`，而 `saveFile` 是 `withContext(io) { locks.withLock { ... } }`（`RepoRepository.kt:310`）——第一个挂起点就会响应取消。`onBack()` 在同一帧内同步执行，协程还没开始跑就被取消了。

**影响**：用户在"有未保存的修改"弹窗里选「保存并退出」，**文件没写盘、退出后改动消失**。这比 1.1 更容易触发，因为它是明确写着"保存"的按钮。

**建议**：`save()` 改成 `suspend fun saveAndWait(): Boolean`，在 `onConfirm` 的 `rememberCoroutineScope()` 里 `if (saveAndWait()) onBack()`；失败时留在页面并提示。

### 1.3 保存期间的输入被标记成「已保存」

**证据**：`EditorViewModel.kt:168-181`，成功回调无条件 `original = current.content; dirty = false`，`current` 是**发起保存时的快照**。若保存期间用户继续输入（IO 有几十毫秒窗口，自动保存开启时更频繁），新输入的内容会被当成已保存，退出时不再拦截。

**建议**：成功后比对 `_state.value.content == current.content` 才清 `dirty`；否则保留 dirty 并提示"已保存到 X，之后又有新改动"。

### 1.4 点远端分支建出来的不是远端那个提交

**证据**：`RepoDetailViewModel.kt:174-196` 的 `checkoutRemote` 只调 `repository.createBranch(local, checkout = true)`；`GitRepo.kt:115-121` 的 `createBranch` 以**当前 HEAD** 为起点，既不读 `refs/remotes/origin/x`，也不写 upstream。

**影响**：在 `feature` 分支上点 `origin/master`，会得到一个和 `feature` 一模一样的本地 `master`（如果本地已有 `master` 则直接报"分支已存在"）。README 与 CHANGELOG 都写着"点远端分支建同名本地分支并切过去"，用户会以为拿到了远端代码。

**建议**：`createBranch(name, startPoint = null, checkout)`，`checkoutRemote` 传 `refs/remotes/origin/x` 的 oid；顺带写 `branch.<name>.remote/merge` 配置（或至少在建分支成功的提示里说明"基于 origin/x"）。

### 1.5 生物识别可被进程恢复绕过

**证据**：`app/.../BiometricGate.kt:82` `var unlocked by rememberSaveable { mutableStateOf(false) }`。`rememberSaveable` 会随 Activity 的 saved state 一起恢复——进程被系统回收后重建、或转屏重建，`unlocked` 直接恢复成 `true`，不再校验。

**影响**：README「已知限制」写的是"冷启动 / Activity 重建时校验"，实际两者都可能跳过；对"给别人看手机时挡一下"这个目标来说，门禁是可绕过的。

**建议**：用 `remember`（配置变更也会重新校验），或显式在 `ON_STOP` 时把 `unlocked` 置 false；同时把 README 的措辞改成与实现一致。

## 4. 做得好的地方

1. **二进制格式不靠"看起来对"**：`GitIndex.read` 校验 SHA-1 与越界（`:112-121`），`ObjectDatabase.readLoose` 复核对象 SHA-1（`:87-90`），`PackIngest` 校验 pack 尾部 checksum（`:41-44`）。
2. **有取舍、有注释**：`PackIngest` 明写"不做 idx 落盘，代价是目录更碎"；`LineDiff` 明写大文件降级与编辑距离上限；`GpDialog` 明写为什么不用 AlertDialog。
3. **并发有锁**：`RepoRepository` 的写操作统一走 `RepoLockRegistry` 按 repoId 串行（`:362-373`），UI 层不会写坏 index。
4. **不 destructive 迁移**：`DatabaseFactory` 明确注释"宁可抛错也不删用户数据"，并注册了迁移。
5. **`status()` 的 racy-clean 处理**（`GitRepo.kt:199-209`）——size 快路径 + mtime + 同秒回退哈希，这是真懂 git 才会写的细节。
6. **真实 git 对拍**：`MergeTest` 用真实 `git merge` 校验两个父提交、`UU` 状态、abort 后工作区一致。
